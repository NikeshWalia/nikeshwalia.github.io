Architecture

Test platform UI & E2E API · contract · security Database
Running system React storefront FastAPI backend PostgreSQL Payment provider (separate service)
Evidence pytest Allure report GitHub Actions

Nothing is mocked in place of the real thing. The tests drive a running stack over HTTP and SQL, and the payment provider is a separate service that can genuinely time out, because an in-process mock would only test the mock.

Constraint

  • Most testing portfolios automate somebody else’s demo site, which caps what you can prove.
  • Race conditions, money rounding and authorisation bugs only show up when you control the system under test.

Test strategy

  • Each rule is proved at the cheapest layer that can prove it, then again where it actually matters. Stock limits: unit, then API, then a database CHECK, then a concurrency test.
  • Nothing shared is mutable. Every test creates its own state with a UUID identity, so it cannot collide across parallel workers.
  • Nothing sleeps. Waiting is Playwright auto-waiting or an explicit condition poll, never a fixed delay.
  • Nothing is hardcoded. URLs, credentials and DSNs come from the environment, so the same suite runs locally, in Compose and in CI.
  • That isolation is what buys the parallelism: the backend suite drops from 376s to 140s, a 2.7x speed up, because tests never wait on each other.

Failure handling

  • Four test cards select the payment outcome per request, so a dozen failure tests run in parallel without fighting over shared state.
  • A decline restores stock. A timeout deliberately does not: nothing knows whether money moved, so the order stays pending rather than guessing.
  • Failures attach a screenshot, a video and a Playwright trace. Passing tests attach none, so a CI run does not produce hundreds of megabytes nobody opens.

What I'd change

  • Mutation testing. The only honest way to find out whether these 916 tests would catch a regression, rather than assuming they would.
  • A payment reconciliation job to close the timeout gap, plus the tests that prove it settles a pending order.
  • axe-core in the UI suite. The markup uses roles and labels correctly, but nothing currently verifies that.

What actually runs

Defects the suite found

Real bugs in the application, caught during development and fixed. A suite that never caught anything would not have earned any confidence.

  1. Critical
    Two customers bought the same unit

    Symptom: with one item left, two concurrent checkouts both succeeded and both were charged.

    Root cause: the row lock was working. The bug was one layer up. Checkout had already loaded those inventory rows to price the cart, so they sat in the ORM identity map. The locking query blocked correctly, then handed back the cached object instead of the freshly read row. A textbook lost update.

    Fix: .with_for_update().execution_options(populate_existing=True)

    The two thread version reproduces every time. The six thread version passed by luck, which is exactly how this class of bug reaches production.

    test_the_last_unit_goes_to_exactly_one_of_two_buyers
  2. Critical
    One character could 500 any endpoint

    Symptom: an unhandled 500 on search, registration, addresses and admin search, from any anonymous caller.

    Root cause: PostgreSQL text columns cannot store a NUL byte. Found by a parametrised injection sweep, not by guessing.

    Fix: one middleware that rejects it as a 422, checking two encodings, because JSON transmits NUL as a six character escape rather than a raw byte.

    test_a_nul_byte_is_refused_cleanly_rather_than_causing_a_500
  3. High
    A corrupt password hash crashed login

    Symptom: the request died at the ASGI layer, below the application’s own error handling.

    Root cause: bcrypt with a truncated hash makes the Rust extension panic, and that exception inherits from BaseException, so it sailed straight past except Exception and the global handler.

    Fix: validate the hash structure before the call is ever reached.

    test_a_corrupt_hash_returns_false_rather_than_raising
  4. Medium
    A withdrawn product looked like a broken link

    Root cause: the documented 409 branch was unreachable. The lookup filtered inactive products out first, so a withdrawn item always returned 404 and the customer could not tell the difference.

    test_adding_a_deactivated_product_is_rejected_as_unavailable
  5. Medium
    A cart could not be fixed once stock fell short

    Root cause: with 3 in the cart and 1 in stock, stepping down to 2 was rejected, while the cart happily kept 3. The only escape was emptying the basket.

    Fix: reductions are always allowed. Only increases are checked against stock.

    test_reducing_the_quantity_re_enables_checkout

Restaurant Monitoring System: Selenium suite

A configurable Selenium and Python framework for end to end monitoring runs. Retry, timeout and redirect handling live in the runner rather than being sprinkled through individual tests, so adding an environment or a flow is configuration instead of new code.

Constraint

  • Flaky network and redirect chains made naive assertions unreliable.
  • 500+ live URLs needed checking every release, and every run ended with a hand written report of what passed and why things failed.

Approach

  • Retry with backoff at the runner level, not per test.
  • Explicit waits over fixed sleeps. No time.sleep() anywhere.
  • Redirect chains followed and asserted on the final resolved URL.

Outcome

  • Replaced roughly ~70% of the manual regression pass.
  • Excel report generated per run: result, failure reason, timestamp.
  • Adding an environment or flow is configuration, not new code.

What I'd change

  • Move reporting to JUnit XML so CI can consume it natively, which is what I did on the later projects.
  • Quarantine flaky tests automatically instead of retrying everything blindly.
