Work: Three systems, and what they cost to build

Each one replaced something that was being done by hand. Expand any card for the constraint, the approach and what I'd change with more time.

01 · Automation framework · Personal project

Order Meal: Selenium automation suite

A configurable Selenium + Python framework for end-to-end e-commerce flows. Retry, timeout and redirect handling live in the runner rather than being sprinkled through individual tests, so adding an environment or a flow is configuration instead of new code.

Read the engineering detail Hide detail

Constraint

  • Flaky network and redirect chains made naive assertions unreliable.
  • Every run ended with a hand-written report of what passed and why things failed.

Approach

  • Retry with backoff at the runner level, not per test.
  • Explicit waits over fixed sleeps. No time.sleep() anywhere.
  • Redirect chains followed and asserted on the final resolved URL.

Outcome

  • Excel report generated per run: result, failure reason, timestamp.
  • Adding an environment or flow is configuration, not new code.

What I'd change

  • Move reporting to JUnit XML so CI can consume it natively.
  • Quarantine flaky tests automatically instead of blanket retries.
02 · Internal tooling · Techsapphire

SQL test-data factory

A reusable provisioning system that standardised test data across environments. It removed the manual database prep every sprint opened with, and made QA, staging and production mirrors consistent by default.

Read the engineering detail Hide detail

Constraint

  • Every sprint began with hand-built database state.
  • Environments drifted, so failures were often environmental, not real.

Approach

  • One repeatable provisioning step per environment.
  • Seed data defined once and reused, instead of per-tester improvisation.

Outcome

  • Per-sprint setup overhead removed.
  • Environment-drift defects stopped appearing in triage.

What I'd change

  • Version the seed sets so a run pins the exact data it used.
  • Teardown as a first-class step, not a manual cleanup.
03 · Machine learning · Personal project

CropCraft: crop recommendation service

A TensorFlow classifier recommending crops from multi-feature soil and weather data, tuned to ~85% accuracy through systematic hyperparameter search and served as a Flask REST API.

Read the engineering detail Hide detail

Approach

  • Systematic hyperparameter search rather than one-off tuning.
  • Model served over HTTP so any client can consume predictions.

Outcome

  • ~85% classification accuracy on multi-feature input.
  • Real-time predictions via a Flask REST endpoint.

Testing view

  • The interesting cases are the boundaries: inputs at the edges of each feature range.
  • A model endpoint still needs schema, error and latency assertions like any other API.

What I'd change

  • Report accuracy against a stated baseline and a held-out split, not as a bare number.
  • Pin the training data and hyperparameters so a result can be reproduced, not just quoted.
