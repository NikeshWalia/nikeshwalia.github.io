Defect write up

The lock worked. Two customers still bought the same unit.

A row lock that blocked exactly as documented, an ORM that helpfully handed back the stale object anyway, and the reason a two thread test caught what a six thread test missed.

Nikesh Walia, QA Engineer 6 minute read Found in ShopSphere

ShopSphere is an e-commerce application I built so that the test platform around it would have something real to run against. Its checkout is the part I trust least, because it is the part where two people can want the same thing at the same moment. This is the bug that came out of it, and it is the most instructive one I have found, because every individual piece of the system was behaving correctly.

The symptom

One unit of a product in stock. Two customers checked out simultaneously. Both received a 201 Created. Both were charged. Stock finished at zero.

That last detail is what made it slippery. An oversell usually announces itself with a negative number, and a negative number is easy to alert on. Here the final stock value was exactly what a correct run would have produced. Nothing in the database looked wrong afterwards. The only evidence was two paid orders for one item.

The obvious explanation was wrong

The checkout path already took a row lock before touching stock, a SELECT ... FOR UPDATE over the inventory rows in the basket. My first assumption was the ordinary one: the lock was missing, or it was being taken after the read instead of before it.

It was not. The lock was firing, and it was doing its job. The second transaction genuinely blocked and genuinely waited until the first one committed. If you had watched the two transactions in the database, you would have seen textbook serialisation.

The lock was not the bug. The bug was one layer above the lock, in the object the lock handed back.

What was actually happening

Checkout reads the inventory rows twice. Pricing the basket joins inventory to work out what the customer owes, so by the time the locking query runs, those same rows are already loaded into SQLAlchemy's session and sitting in its identity map.

SQLAlchemy, by default, will not overwrite attributes it has already populated on an object in the session. So the sequence went like this. The locking query blocked, correctly. It waited for the other transaction, correctly. It read the fresh row from the database, correctly. Then it looked at that row, recognised the object it already had in memory, and returned the cached copy instead.

Both transactions therefore serialised properly and then both read quantity == 1 from their own private cache. Both passed validation. Both wrote quantity = 0. Both customers were charged. A textbook lost update, produced by a lock that never once misbehaved.

The fix

One execution option.

populate_existing=True forces the attributes to be refreshed from the locked row rather than served from the identity map. The second transaction now sees the zero that the first one wrote, fails its stock check, and is correctly refused.

The order_by on a sorted list of ids is the other load bearing detail, and it is there for a different race. Two transactions that lock the same two rows in opposite orders deadlock. Acquiring them in a globally consistent order means the second transaction simply waits instead.

The test that proves it

The assertion is on the aggregate outcome, not on any one response. Neither request is expected to win. What must be true is that exactly one of them does, and that the database agrees afterwards. Asserting on a single response would have made the test order dependent, and an order dependent concurrency test is worse than no test at all.

Each shopper also carries its own HTTP client. That is not tidiness. If the threads share a connection pool, the supposedly concurrent requests serialise inside the HTTP library before they ever reach the server, and the test proves nothing while passing cleanly.

Why two threads beat six

There is a six thread version of this race in the same file. It passed.

The two thread version failed on every single run.

More load is not more pressure. With six threads competing, the timing spread widens, and something almost always serialises them by accident before they reach the window where the bug lives. With exactly two, both transactions reliably get to the read before either one commits, which is precisely the interval the lost update needs. Sharpening the race mattered far more than widening it.

A concurrency bug that survives your load test is not rare. It is the normal case. The load test is the thing that reassured everybody on the way to production.

What I took from it

  • A lock that fires is not a lock that works. Verify what the query hands back, not merely that it blocked. Everything I could observe about the lock itself was healthy.
  • Look one layer above the thing everyone inspects. The database was right, the SQL was right, and the defect lived in the object mapper sitting between them.
  • Design the race, do not just add threads. The sharpest version of a race is usually the smallest one that still contends.
  • Assert on aggregates. In a concurrent test, no individual participant has a predictable result. The invariant does.
